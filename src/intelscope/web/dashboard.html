03

IOC triage

Paste indicators from a report or an alert, defanged is fine. Each one is checked against up to twelve threat-intel sources and gets one score and a verdict, with the evidence behind it, so you know what to look at first.

Indicators

IPs, domains, URLs and file hashes, as many as you like. Separate them with spaces, tabs, commas, semicolons or new lines, in any mix. Defanged is fine, and so are ports, quotes and brackets around them; comments after # are ignored.

Sources

Add keys and switch sources on or off under API keys. Shodan InternetDB, RDAP, passive DNS, urlscan, GreyNoise and the ASN check need no key. Run sends the indicators to every ready source, so keep victim-specific artifacts out of it (see OPSEC).

Add to IOC list

Saves the results shown above, with the label and details you set here, and copies the evidence from every source into the row. The same indicator from the same source updates its row instead of adding a second one.

Verdicts are decision support, not ground truth. Verify before blocking. STIX export contains malicious and suspicious indicators only.

04

IOC tracker

Keep the indicators you are following, with the label they must be handled under, why they matter, where you got them and when. One row per indicator per source. Export the lot as a Markdown table for notes, tickets or a handover.

Add indicators

IPs, domains, URLs and hashes, defanged is fine. The fields below apply to every indicator you add in one go. Adding the same indicator from the same source again updates its row.

Export

The Markdown file carries the highest TLP of its rows at the top: treat the whole file at that label. To share something wider, export only the rows up to a lower label.

Import reads a table with an IOC column (and any of TLP, Source, Date, Context), such as an earlier export. You can also paste the table into the box on the left. Rows already there are updated, not duplicated. An Evidence section under the table, as this tool exports it, is read back into the rows too.

08

Images

Leak-site proof screenshots and actor avatars carry metadata, artefacts and reusable hashes. Everything below runs locally, so evidence images never leave your machine.

Handling Work on copies. Hash the original first and record it in the case file so you can prove the image you analysed is the image you received.

Local image inspector

Reads EXIF, GPS, maker fields, PNG text chunks and XMP. Computes SHA-256, dHash and aHash.

Drop an image here, or click to choose. Nothing is uploaded.

Perceptual hash compare

Two dHashes, Hamming distance. Under 10 usually means the same source image, useful for matching a leak screenshot to an earlier post.

11

Darkweb

Leak portals, negotiation panels and forum profiles. Treat every onion as hostile infrastructure that logs you.

Before you click Onion links open in a normal browser will fail, and clearnet mirrors of leak sites will log your address. Use a dedicated Tor Browser in an isolated VM, and never authenticate to a negotiation portal with a real victim key unless the incident lead has authorised it. Loading a victim chat can reset a countdown timer.

Onion address validator

Full v3 check: base32 decode, version byte, and SHA3-256 checksum. Confirms an address is genuine before you spend time chasing a typo.

Ransomware leak trackers

Clearnet aggregators that mirror victim postings, so you can often avoid touching the portal itself.

Artifact lab

Local validators and converters. Use these before any external lookup so you do not query third parties with a malformed or misread identifier.

TOX ID validator

76 hex characters: 32 byte public key, 4 byte nospam, 2 byte checksum. The checksum is XOR-folded over the first 36 bytes, so a transcription error is caught here rather than after you message the wrong person.

Hash identifier

Length and charset classification, plus direct sandbox and repository lookups.

Encode / decode

Timestamp converter

Unix seconds and milliseconds, Windows FILETIME, WebKit/Chrome, LDAP and ISO.

14

Crypto trail

Ransom addresses are one of the few artefacts that persist across victims. Validate the address offline, then trace it on chain and check whether it is already reported.

Address validator

Bitcoin base58check and bech32 checksums, Ethereum EIP-55 casing, Monero prefix and length. Real validation, not a pattern guess.

Monero reality check

Monero is the default demand for most current crews precisely because ring signatures and stealth addresses defeat address clustering. A Monero address is still worth recording: it correlates victims of the same affiliate, appears in other notes, and matters for reporting. Do not promise the incident lead a chain trace you cannot deliver. Where a crew offers a Bitcoin option at a premium, that path is the one worth tracing.
